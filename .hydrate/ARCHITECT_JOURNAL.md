# hydrate — System Documentation

## 1. Living Architecture & System Overview
`@nemzilla/hydrate` is a zero-dependency Node.js CLI (`bin/cli.js`) that scaffolds and maintains a 3-artifact AI context harness inside any target repo:

- **`CLAUDE.md`** — Operating rules & AI execution protocol, rendered from `templates/CLAUDE.md.template`.
- **`.hydrate/CURRENT_UOW.md`** — The active Unit of Work execution canvas, rendered from `templates/CURRENT_UOW.md.template`.
- **`docs/SYSTEM.md`** — This file's own shape: living architecture notes, roadmap/task index, backlog, and an append-only decision log, rendered from `templates/SYSTEM.md.template`.

**Module map**
- `src/templates.js` — loads/renders `templates/*.template` files (`{{PLACEHOLDER}}` substitution).
- `src/init.js` — `scaffold()` idempotently writes the 3 canonical artifacts into a target repo.
- `bin/cli.js` — command dispatch for the strict v2 surface (`init`, `prompt`, `clip`, `complete`, `help`, plus `-h`/`-v`/`?` aliases); owns `prompt` (sync active UOW payload from `docs/SYSTEM.md` + `CLAUDE.md`) and `complete` (mark done in `docs/SYSTEM.md`, log to Section 4, archive, reset) directly.
- `src/clipboard.js`, `src/help.js` — clipboard piping and CLI help/usage text.

**Pruned in UOW-02 (v2 Refactor):** `src/adopt.js`, `src/inject.js`, `src/discover.js`, `src/guide.js`, `src/setupCc.js` — the v1 `adopt`/`inject`/`iterate`/`setup-cc`/`greenfield`/`brownfield`/`next`/`lost`/`copy` command entry points and their backing modules.

**Implement Journal & Archive Validation Utility (`hydrate check`)**

- **New module:** `src/commands/check.js` exports `runCheck(cwd)` (pure logic, returns `{ ok, errors, warnings, checkedUows }`) and `formatReport(result)` (pure string rendering) — kept separate from `bin/cli.js` so the validation logic is independently unit-testable, consistent with `src/init.js`'s `scaffold()` split.

- **Contract — journal-entry assertions per archived UOW ID:**

  - `.hydrate/DEV_JOURNAL.md` / `.hydrate/ARCHITECT_JOURNAL.md`: lenient check — any markdown heading line (`#` through `######`) containing the UOW-ID token.
- **Trade-off / spec deviation (confirmed against real repo state, not re-litigated with the Product Owner given the Fast-Path Protocol):** UOW-HYDRATE-02's payload specified `## [<UOW-ID>]` literally for the dev/architect journal headings. Chose the lenient heading matcher over amending the two hand-maintained journal files to fit the spec's format, since `DEV_JOURNAL.md`/`ARCHITECT_JOURNAL.md` are explicitly hand-maintained artifacts under CLAUDE.md §4, not `hydrate`-generated ones — `hydrate check`'s job is to validate against this project's actual established convention, not to prescribe a new one.
- **New heuristic:** `findUnarchivedCompletedUow()` reuses the same "no remaining `- [ ]` tasks" signal `handleComplete()`'s `findOpenTasks()` already encodes in `bin/cli.js`, applied read-only to flag (not act on) a fully-checked-off `CURRENT_UOW.md` that hasn't been archived yet.

### UOW-HYDRATE-03 — completed 2026-09-01
**Implement High-Density Context Compiler (`hydrate context`)**

- **New module:** `src/commands/context.js` exports `buildContext(cwd, { depth })` (pure logic, returns the compiled string) plus two testable extraction helpers (`extractRecentArchitectEntries()`, `extractActiveEpics()`) — continues the `src/commands/*.js` pattern established by `check.js`: business logic lives outside `bin/cli.js`, which only owns argv parsing and I/O side effects (`handleContext()`).
- **New CLI surface:** `hydrate context [--clip|-c] [--depth <n>|--depth=<n>]` — read-only across `.hydrate/`. Prints the compiled payload to stdout unconditionally; `--clip` additionally pipes it through `copyWithFeedback()` (the same clipboard utility `hydrate clip`/`hydrate prompt --copy` already use) without reprinting it on the no-tool-found fallback.
- **Contract — payload shape:** header (project name via `package.json`/dirname, ISO timestamp) → `## Active Scope` (full trimmed `.hydrate/CURRENT_UOW.md`, or a "no active UOW" notice) → `## Architectural Context` (tail `depth` `### `-delimited blocks from `.hydrate/ARCHITECT_JOURNAL.md`, most-recent-last) → `## Macro Roadmap` (`.hydrate/ROADMAP.md`'s `## Section 1: Scheduled Roadmap Items` section, reusing the same "## Section 1" prefix convention `findNextPendingUow()` in `bin/cli.js` already relies on). Each section degrades independently to its own fallback notice when the source file/section is absent, rather than failing the whole command — deliberate, since `hydrate context` is meant to be usable at any point in a repo's `.hydrate/` lifecycle (freshly-initted, mid-UOW, or between UOWs).
- **Trade-off:** `context.js` duplicates a small `getProjectName()` helper rather than importing `bin/cli.js`'s — `bin/cli.js` runs its full command-dispatch switch as top-level side-effecting code on require, so it is not safe to `require()` from a library module or test file. Same constraint `check.js`/`check.test.js` already work around by driving `hydrate check` through `spawnSync` at the CLI boundary instead.
- **Depth parsing convention:** `--depth <n>` (space form) and `--depth=<n>` (equals form) are both accepted, mirroring `hydrate prompt --chunk-size=<bytes>`'s existing precedent; a non-positive or non-numeric value is silently ignored and the default (3) is used, rather than erroring — consistent with how `--chunk-size` already degrades.

### UOW-HYDRATE-05 — completed 2026-09-01
**Implement Smart State Machine & Session Reconciler (`hydrate checkup`)**

- **New module:** `src/commands/checkup.js` exports `runCheckup(cwd)` (pure logic, returns `{ state, message, uowId?, openTasks?, modifiedFiles?, gitStatus, tests? }`) and `formatCheckupReport(result)` (pure string rendering) — continues the `src/commands/*.js` split established by `check.js`/`context.js`/`export-portfolio.js`.
- **New CLI surface:** `hydrate checkup` (alias `hydrate status`) — read-only against `.hydrate/`; its only side effects are a `git status --porcelain` shell-out and, conditionally, an `npm test` shell-out (see below).
- **Contract — state machine:** `runCheckup()` resolves to exactly one of `error` (`.hydrate/` missing), `clean-slate` (`CURRENT_UOW.md` empty or the "All UOWs are complete!" placeholder), `unarchived-done` (every `- [ ]` task in `CURRENT_UOW.md` checked off, UOW ID not already present in `.hydrate/archive/`, and `npm test` passes or can't be run), `broken-build` (same as `unarchived-done` but `npm test` exits non-zero), `in-progress-dirty` (open tasks remain and `git status --porcelain` reports modified files), or `in-progress-clean` (open tasks remain, clean tree). Precedence is: placeholder check first, then the all-tasks-checked branch (which is the only branch that shells out to `npm test`), then the dirty/clean split — a UOW can be simultaneously "complete" and "dirty" (uncommitted new code before archiving), so completeness is checked independently of, and takes priority over, tree cleanliness.
- **Contract — "already archived" guard:** reuses `check.js`'s convention of treating `.hydrate/archive/<UOW-ID>.md` filename stems as the canonical archived-ID list, so a `CURRENT_UOW.md` that still holds a fully-checked-off payload whose ID is already archived (stale, not yet reset by `hydrate complete`) falls through to the in-progress branches instead of re-reporting "complete but unarchived".
- **Contract — roadmap "pending items" signal:** deliberately format-agnostic — `.hydrate/ROADMAP.md` has no single fixed convention across this repo's own history (`## Section 1`/checkbox items per `context.js`/`export-portfolio.js`'s parsing vs. this repo's current free-form `⚬` epic bullets), so "pending items exist" is just "any non-heading, non-blank line exists beneath the title", not a `## Section 1` extraction like `context.js`/`bin/cli.js`'s `findNextPendingUow()` use. A future UOW that needs a structured roadmap-items count should extract via `context.js`'s existing `extractActiveEpics()` instead of duplicating a stricter parser here.
- **Trade-off — when `npm test` runs:** only in the all-tasks-checked branch, not on every invocation — `hydrate checkup` is meant to be a fast, frequent session-start check; the in-progress states don't need a test-suite verdict to answer "what state am I in", and running the full suite unconditionally would make the command noticeably slower for the common case with no corresponding benefit.
- **Resilience:** both shell-outs degrade gracefully — `getGitStatus()` treats a spawn failure or non-zero `git status` exit (not a repo, `git` missing) identically as "no git signal available" (`available: false`); `runTestSuite()` treats a spawn failure (`npm` missing) as `{ ran: false }`, which the `unarchived-done`/`broken-build` branch condition (`tests.ran && !tests.passed`) treats the same as a passing run — a UOW is never blocked from being reported "complete" just because the test runner itself couldn't be invoked in the current environment.
- **Exit codes:** `0` for every state except `error` and `broken-build` (`1`) — `hydrate checkup` is an informational reconciler, not a CI gate; `broken-build` is the one state that represents an actual regression worth a non-zero exit.

### UOW-HYDRATE-06 — completed 2026-09-01
**Implement Clipboard Ingress Engine & Interactive Prompting (`hydrate ingest`)**

- **New module:** `src/commands/ingest.js` exports an async `runIngest(cwd, options)` — the first `src/commands/*.js` module with real interactive I/O rather than pure read/format logic, since `hydrate ingest` needs a live menu prompt. Every I/O seam (`readClipboard`, `input`/`output` streams, `log`/`error`) is a constructor-injected default, keeping the module fully unit-testable without a pty, consistent with the DI style `src/clipboard.js`'s `copyToClipboard({ spawn })` already established.
- **New CLI surface:** `hydrate ingest` (alias `hydrate paste`), `[--yes|-y]` for non-interactive/headless use.
- **Spec deviation — module layout:** the UOW payload specified `src/utils/clipboard.js` and `src/utils/ui.js`. This repo has no `src/utils/` directory and no precedent for one; clipboard I/O already lives in `src/clipboard.js` (extended in place) and the interactive UI logic lives inline in `ingest.js` (the payload's own stated fallback: "`src/utils/ui.js` **or within ingest.js**"). Chose the path that matches this repo's actual established module layout over introducing a new directory convention for a single command.
- **New contract — clipboard read:** `readFromClipboard()`/`pasteCandidatesForPlatform()` added to `src/clipboard.js`, mirroring `copyToClipboard()`/`candidatesForPlatform()`'s exact platform-dispatch + injectable-`spawn` shape. Returns the tool's stdout on success or `null` if no candidate tool is available — `null` is treated by `runIngest()` as a hard error (distinct from "clipboard is empty," which a validation failure covers), since silently proceeding with unreadable clipboard state has no safe behavior.
- **New contract — UOW payload validation:** `isValidUowPayload()` requires a `#`-`###` `UOW-...` header AND at least one of `Goal & Context` / `Surgical Scope` / `Acceptance Criteria` (case-insensitive). Requiring both narrows false positives from a stray `# UOW-` mention in unrelated copied text; validation runs before any file is touched, so a rejected clipboard leaves `.hydrate/CURRENT_UOW.md` provably untouched.
- **New contract — state-branching menu:** reuses the same empty/placeholder detection `checkup.js`'s `isPlaceholderUow()` already encodes (`isEmptyUow()` here). Empty state offers `[1] Apply` / `[2] Chat-Exit`; active/uncompleted state offers `[1] Archive-and-swap` / `[2] Overwrite` / `[3] Chat-Exit`. Any unrecognized input in either menu resolves to the chat-exit action rather than erroring — the spec's `[Chat]` option is meant to always be a safe, always-available fallback, not just one of several equally-weighted numbered choices.
- **New contract — `--yes` default behavior:** the non-interactive flag archives any active UOW (if present) before applying the clipboard payload — i.e., it takes the "archive-and-swap" branch, never "overwrite" — since a headless/automated invocation should default to the non-destructive path; nothing is ever lost, only relocated to `.hydrate/archive/`.
- **Reused abstraction:** archive-file naming (`.hydrate/archive/<UOW-ID>.md`) and the UOW-ID extraction regex (`/UOW-[A-Za-z0-9-]+/`) both match `bin/cli.js`'s `handleComplete()`/`archiveCurrentUow()` convention exactly (including the same fallback path when no ID is resolvable, here synthesized as `UOW-UNKNOWN-<timestamp>` rather than crashing).

### UOW-HYDRATE-10 — completed 2026-09-01
**Zero-Touch Auto-Provisioning & Unified `/hydrate` Interface**

- **New abstraction — `.claude/commands/` provisioning as a standalone capability**: extracted `scaffoldClaudeCommands(cwd)` out of `src/init.js`'s `scaffold()` so slash-command provisioning is no longer bundled exclusively with the full `CLAUDE.md` + `.hydrate/` scaffold. This lets `bin/postinstall.js` provision *just* the Claude Code integration into a host project on `npm install`, without forcing that project into the full Hydrate harness (`hydrate init` remains the explicit, opt-in path for the rest).
- **Trade-off — postinstall supersedes global scaffolding**: `package.json`'s `"postinstall"` now points at `bin/postinstall.js` instead of `bin/setup-global.js`, replacing the old behavior (writing `/hydrate` and `/hydrate-architect` into the user's global `~/.claude/commands/`) with per-project scaffolding into the *host* project's `.claude/commands/` via `INIT_CWD`. This is a deliberate architectural shift toward "zero-touch, project-local, without manual `hydrate init`" per the UOW's framing — `bin/setup-global.js` itself was left in the repo untouched (not deleted) since it wasn't in the UOW's affected-files list, but it is no longer invoked by any script.
- **Contract — chronological UOW ordering uses filesystem mtime, not filename parsing**: `src/commands/uow.js`'s `listUows()`/`getLastUow()` sort `.hydrate/archive/*.md` by `mtimeMs`. This repo's own archive already has three incompatible ID schemes (`UOW-01`, `UOW-HYDRATE-08`, `UOW-HYDRATE-01-HOTFIX`), so no string/numeric sort on the ID itself can produce a correct chronological order across all of them — mtime is the one signal that's always true regardless of naming convention, since `hydrate complete` writes the archive file at the exact moment of completion.
- **Contract — `/hydrate` master command is prompt-composition, not new CLI surface**: `templates/.claude/commands/hydrate.md.template`'s "checkup → auto-archive-if-done → clip context" behavior is expressed entirely as sequenced Bash-tool instructions over three *existing* `hydrate` CLI verbs (`checkup`, `complete`, `context --clip`), not a new `hydrate hydrate` meta-command. Keeps the established precedent (every `templates/.claude/commands/*.md.template` file is a thin prompt wrapper, all actual logic lives in the CLI) intact rather than introducing a second place UOW-completion auto-archiving could happen.
- **Scope note**: this repo's own hand-written `.claude/commands/hydrate.md` (predating the UOW-HYDRATE-07 template scaffold, previously just `hydrate prompt --copy`) was overwritten to match the new unified template — the only place an existing file's *content* (not just presence) was intentionally changed as part of this UOW, since the master `/hydrate` command's new behavior needed to actually be live in this session for the UOW's own verification step 4 to be checkable.

### UOW-HYDRATE-14 — Global Lifecycle Engine & Workspace Sync (2026-09-12)
- **New abstraction — the "delimited managed block"**: `src/utils/managed-block.js` establishes a reusable pattern (create-fresh / append-if-absent / replace-if-present, all keyed off HTML-comment markers) for injecting Hydrate-owned content into a file a Product Owner also edits. `scaffold()`'s CLAUDE.md step now uses it, which is a real contract change: CLAUDE.md is the one scaffolded artifact that is no longer strictly skip-if-exists — every other `.hydrate/`/`.claude/commands/`/`docs/` artifact keeps the original idempotent skip-if-exists contract from `hydrate init`.
- **Contract — `hydrate sync` vs. `hydrate init` overwrite semantics diverge on purpose**: `scaffoldClaudeCommands()` (used by `init`/postinstall) is skip-if-exists; `syncRepo()` (new, `src/commands/sync.js`) force-overwrites every `.claude/commands/hydrate-*.md` to the current template render regardless of local edits. This is intentional — `sync`'s entire purpose is enforcing parity with the installed hydrate version, whereas `init` must never clobber a Product Owner's customized slash command. Both commands funnel through the same `applyManagedBlock()` for CLAUDE.md, so the *rules* block behaves identically either way; only the command-template overwrite policy differs.
- **Trade-off — `--recursive` is downward-only**: Items 2.1/2.3 both describe scanning "parent/child directories," but an upward walk from an arbitrary cwd toward the filesystem root has no natural bound and is unsafe for a flag invoked from anywhere. `src/utils/repo-scan.js`'s `findRepoRoots()` only descends from the given `--path` (default cwd). Documented in both commands' help text and `hydrate sync`/`hydrate eject`'s doc comments so this scoping decision is discoverable, not silent.
- **Trade-off — `hydrate hook` doesn't use git's template-dir/`core.hooksPath` mechanism**: the spec's primary "Option A" (global git template hooks dir) doesn't actually work for this use case — git has no hook event that fires on a bare `git init` with no subsequent commit/checkout. Implemented the spec's own "Option B" instead: a `git` shell-function wrapper in the user's shell rc, using the same idempotent-delimited-block shape as `managed-block.js` (kept as an independent small implementation since the marker syntax is shell-comment, not HTML-comment — not worth generalizing a 15-line primitive for one caller).
- **Contract — version-drift checking is TTY-gated, not env-flag-gated**: `bin/cli.js`'s `handleCheckup()` only calls the real npm-registry lookup when `process.stdout.isTTY && !process.env.CI`. This means every CLI-level test (spawned via `child_process.spawnSync`, always non-TTY) exercises `runCheckup()`/`formatCheckupReport()` exactly as before with zero network dependency, while a genuine interactive terminal session gets the upgrade nag — the same convention npm's own update-notifier tooling uses. `runCheckup()` itself was left completely unmodified; the drift check is a separate, best-effort (try/catch-wrapped) step layered on top in `bin/cli.js` only, not inside the pure state-reconciliation function.
- **Trade-off — `hydrate update`/`hydrate hook enable` are unit-tested only, never executed for real**: both perform a real, hard-to-reverse side effect on the operator's machine (a global npm install; a shell rc edit). Both take every I/O dependency (`spawn`, `sync`, `rcPath`) as an injectable parameter specifically so their business logic has full test coverage without ever needing to actually run `npm install -g` or write to a real `~/.zshrc` during development or CI.
- **Fixed while touching adjacent code**: `hydrate-lfg.md.template` existed on disk since UOW-HYDRATE-08 but was never added to `src/init.js`'s `CLAUDE_COMMANDS` array, so `hydrate init` never actually scaffolded `/hydrate-lfg` into a fresh project. Corrected as part of exporting `CLAUDE_COMMANDS` for `hydrate sync`'s reuse, since sync needed one authoritative list of "every command template that should exist" and a stale list would have made `hydrate sync` silently perpetuate the same gap.

### UOW-HYDRATE-15 — Greenfield Harness Reset & Force Sync (2026-09-12)
- **Contract change — `applyManagedBlock()`'s "no markers" outcome**: UOW-HYDRATE-14 shipped auto-append-if-unmarked as the default. This UOW replaces that outright: the unmarked case is now guard-by-default (`applyManagedBlock()` returns `null`, callers must not write) with `{ force: true }` as the only path to a wholesale replace. There is no longer any code path that appends the block to unmarked content — silently merging Hydrate's rules into a file the operator never opted into managing was the exact problem this UOW exists to fix, so "append" isn't a degraded fallback, it's gone entirely.
- **New optional field, not a new return shape**: `scaffold()`/`syncRepo()` keep their existing return shapes (`created` array; `{repoDir, action, updated}` object) and gain one new optional signal each — a `{ guard: true }` flag on a `created` entry, a `guard: <path>|null` field on a sync result — rather than restructuring either into `{result, warnings}`. Chosen specifically to keep every pre-existing UOW-HYDRATE-14 test assertion about array length / result shape valid except the handful that directly exercised the now-removed append behavior.
- **Scope boundary — `--force` governs exactly two surfaces**: CLAUDE.md's managed block and `.claude/commands/*.md` templates. `.hydrate/` (journals, archive, ROADMAP.md, the active canvas) and `docs/ARCHITECTURE*.md` are never in scope for `--force`, in either `hydrate init` or `hydrate sync` — this was explicit in the UOW's Technical Requirements and is enforced simply by `force` never being threaded into any of those write paths.
- **Trade-off — `--force` fixes "no markers," not "markers exist but content is still duplicated elsewhere in the file"**: discovered via dogfooding on this repo's own `CLAUDE.md`, which has valid markers (from an earlier real `hydrate init` run predating this UOW) wrapping a second, redundant copy of the rules below an original hand-written copy that was never removed. Because markers ARE present, `applyManagedBlock()` takes the "replace between markers" branch unconditionally (force is irrelevant to that branch) and correctly leaves the surrounding content alone — which means the redundant top-of-file prose survives untouched by both plain `sync` and `sync --force`. Extending `--force` to also detect and strip *duplicate, unmarked prose that happens to resemble the managed content* was considered and rejected as unbounded (there's no reliable way to distinguish "duplicated Hydrate rules" from "the operator's own similarly-worded custom rules" without content-diffing against a specific template render, which is fragile across template versions) and out of this UOW's stated scope (replace an unmarked file wholesale — not deduplicate an already-marked one). Left as a manual Product Owner cleanup.
